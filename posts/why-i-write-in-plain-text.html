Why I Write in Plain Text

08 Jun 2025 · 4 min read · plaintextlab

Every few years a new note-taking app arrives and promises to change how you think. It has a beautiful interface, a novel metaphor — networked graphs, infinite canvases, AI sidebars — and for a few weeks it genuinely feels like a new way of working. Then the company raises a Series B, pivots, and your notes are locked inside a proprietary database format you cannot read.

I have been through this cycle enough times that I stopped counting migrations. Evernote to Notion to Obsidian to Roam and back again. Each time I moved, I lost formatting, lost links, lost small things that mattered. The lesson I kept not learning: the format is the durability.

The oldest format that still works

Plain text is not a compromise. It is a decision. A .txt file written in 1985 opens without ceremony on any machine made in the last forty years and every machine likely to be made in the next forty. It has no vendor. It requires no subscription. It has no schema that can be deprecated.

Every other format — even PDF, even HTML — makes assumptions about the rendering environment. Plain text makes exactly one assumption: that the reader can decode ASCII or UTF-8. That assumption has been continuously valid for longer than most of us have been alive.

"Worse is better" is one way to put it. Another: the most robust tool is the one that can fail the least because it promises the least.

The filesystem is already your database

The thing I kept rebuilding inside every app was a filing system. Notebooks, tags, folders, workspaces. At some point I noticed I was recreating the directory tree — badly, inside a walled garden, with extra steps.

With plain text, the filesystem is the database. Files are rows. Folders are categories. The find command is your search. grep is your full-text index. A shell one-liner can answer questions about your entire note archive in milliseconds. 

# Find every note that mentions a topic, sorted by date modified
grep -rl "distributed systems" ~/notes | xargs ls -lt | head -20

No plugin required. No sync to wait for. No monthly fee.

Writing tools vs. thinking tools

There is a useful distinction between tools that help you write and tools that help you think. Note-taking apps are sold as thinking tools — the graph view, the backlinks, the AI that summarises your own notes back at you. In practice, most of the friction they introduce is friction in the tool itself, not in the thinking.

A blank text file and a good editor have the lowest possible interface overhead. There is nothing to click, nothing to configure, nothing between you and the sentence you are trying to write. This is not minimalism as an aesthetic; it is minimalism as a performance characteristic.

The tools I actually use

  • Neovim — for everything from quick notes to long-form drafts
  • fd + ripgrep — for finding and searching files quickly
  • Git — version history for writing, not just code
  • Pandoc — when I need to convert Markdown to anything else

The format is not the point

None of this is to say plain text is the only correct answer. Spreadsheets exist for reasons. Diagrams need different tools. The argument is narrower: for prose — notes, journal entries, drafts, research — text is almost certainly sufficient, and the cost of switching away from it is almost always higher than it appears at the point of migration.

Start with the simplest format that works. Add complexity only when you can name the specific problem it solves. And be suspicious of any tool that makes it easy to put data in and hard to get it back out.
